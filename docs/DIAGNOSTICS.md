# DIAGNOSTICS.md

Спецификация диагностик компилятора SwiftScript. Документ описывает, какие ошибки и предупреждения выдаёт компилятор, в каком формате и с какой позицией. Если код и документ расходятся — это баг.

## Обзор

Диагностика — это сообщение о проблеме в исходном коде. Каждая диагностика имеет позицию, уровень и текст. Компилятор выдаёт диагностики в двух случаях: при синтаксической ошибке (лексической или парсерной) и при ошибке кодогенератора (внутренней).

**Сейчас:** реализован только первый случай. Второй случай — баг компилятора, а не пользователя.

**Планируется:** отдельный проход type checker'а с собственными кодами ошибок.

## Текущее состояние

Диагностика представлена типом `SSError`:

```js
class SSError extends Error {
    constructor(msg, line, col) {
        super(msg);
        this.name = "SSError";
        this.line = line;
        this.col = col;
    }
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `message` | `string` | Текст ошибки на русском языке |
| `line` | `number` | Номер строки, 1-based |
| `col` | `number` | Номер колонки, 1-based |
| `name` | `string` | Всегда `"SSError"` |

Кодов ошибок нет. Уровней нет — все ошибки фатальные. Предупреждений нет.

`compiler.js` перехватывает `SSError` и превращает в объект диагностики:

```js
{
    line: number,
    col: number,
    msg: string,
    severity: "error"
}
```

Любая другая ошибка (внутренняя ошибка компилятора) превращается в диагностику с `line: 1, col: 1`.

## Источники диагностик

### Лексер

| Сообщение | Условие |
|-----------|---------|
| `Незакрытая строка` | Открывающая кавычка без закрывающей до EOF |
| `Неизвестный символ '<c>'` | Символ вне всех лексических классов |

Позиция — начало проблемного места. Для незакрытой строки — открывающая кавычка.

### Парсер

| Сообщение | Условие |
|-----------|---------|
| `Ожидалось <kind> '<value>', получено '<got>'` | Токен не соответствует ожидаемому |
| `Неожиданный токен '<v>'` | Primary не может разобрать токен |
| `Незакрытая функция` | `func ... {` без `}` до EOF |
| `Незакрытая структура` | `struct ... {` без `}` до EOF |
| `Незакрытый enum` | `enum ... {` без `}` до EOF |
| `Незакрытый блок` | `{` без `}` до EOF |
| `Незакрытый switch` | `switch ... {` без `}` до EOF |
| `Незакрытое замыкание` | `{` без `}` до EOF |
| `В структуре ожидалось поле или метод, получено '<v>'` | Не-поле и не-метод в теле struct |
| `В enum ожидался case, получено '<v>'` | Не-`case` в теле enum |
| `В switch ожидался case или default, получено '<v>'` | Не-`case` и не-`default` в теле switch |
| `Интерполяция должна быть выражением` | `\(...)` содержит не-выражение |
| `async должен стоять перед лямбдой` | `async` не перед замыканием |

### Кодогенератор

| Сообщение | Условие |
|-----------|---------|
| `Кодоген: неизвестный стейтмент <k>` | `genStmt` не знает тип |
| `Кодоген: неизвестное выражение <k>` | `genExpr` не знает тип |
| `Кодоген: неизвестный паттерн <k>` | `genPattern` не знает тип |
| `Структура <name>: аргументы должны быть именованными` | Конструктор struct с безымянным аргументом |

Эти ошибки — **баги компилятора**, не пользователя. Пользователь не должен их видеть. Если видит — это значит, что парсер пропустил невалидный AST.

## Формат вывода

### В браузере (playground)

`app.js` выводит диагностики в терминал:

```
✖ 12:5  Ожидалось op '{', получено 'foo'
```

Формат: `✖ <line>:<col>  <msg>`. Строка выделяется классом `.err` с красным цветом.

### В CLI

**Планируется** формат в стиле rustc:

```
path/to/file.sws:12:5: error: expected `{` after function signature
   |
12 | func greet(name: String) -> String
   |                                   ^ expected `{` here
```

**Сейчас:** CLI не реализован. Формат не зафиксирован.

## Позиции

Все диагностики имеют `line` и `col`, оба 1-based.

**Лексер.** Позиция начала проблемного места. Для незакрытой строки — открывающая кавычка. Для неизвестного символа — сам символ.

**Парсер.** Позиция текущего токена (`peek()`). Для ошибок «ожидалось X, получено Y» — токен `Y`. Для ошибок «неожиданный токен» — этот токен.

**Кодогенератор.** Позиция не заполняется. Все ошибки кодогенератора имеют `line: 1, col: 1`. Это сделано, потому что AST не содержит позиций.

> ⚠️ **Внимание:** кодогенератор не может указать позицию ошибки, потому что AST не хранит номера строк и колонок. Если понадобится точная позиция для ошибок кодогенерации, придётся добавить позиции в AST.

## Приоритеты

При наличии нескольких ошибок компилятор сообщает **только первую**. Лексер и парсер останавливаются на первой ошибке.

Это осознанное решение: компилятор для себя, нет смысла в error recovery.

> ℹ️ **Примечание:** при развитии языка может понадобиться вывод всех ошибок за один проход. Это потребует переработки парсера: он должен уметь восстанавливаться после ошибки и продолжать разбор.

## Планируемые коды ошибок

Когда появится type checker, каждому виду ошибки должен соответствовать код. Формат: `E<область><номер>`.

### Синтаксис (E0xxx)

| Код | Сообщение |
|-----|-----------|
| E0001 | unexpected token |
| E0002 | unclosed string literal |
| E0003 | unclosed block |
| E0004 | expected X, got Y |

### Типы (E1xxx)

| Код | Сообщение |
|-----|-----------|
| E1001 | type mismatch |
| E1002 | unknown type |
| E1003 | not a function |
| E1004 | wrong argument count |
| E1005 | not an optional |
| E1006 | cannot infer type |
| E1007 | return type mismatch |
| E1008 | missing return |
| E1009 | undefined identifier |
| E1010 | cannot assign to let |

### Область видимости (E2xxx)

| Код | Сообщение |
|-----|-----------|
| E2001 | duplicate declaration |
| E2002 | use before declaration |

### Внутренние (E9xxx)

| Код | Сообщение |
|-----|-----------|
| E9001 | codegen: unknown node kind |
| E9002 | codegen: struct with unnamed argument |
| E9003 | internal compiler error |

## Планируемые предупреждения

| Код | Сообщение |
|-----|-----------|
| W0001 | unused variable |
| W0002 | unreachable code |
| W0003 | non-exhaustive switch |

Предупреждения не блокируют компиляцию. Флаг `--strict` переводит их в ошибки.

## Инварианты

Для любой диагностики:

1. **`line >= 1`, `col >= 1`.** Позиция всегда валидна.
2. **`msg` непустой.** Пустых сообщений нет.
3. **`severity` — `"error"` или `"warning"`.** Других значений нет.
4. **Ошибки компилятора не смешиваются с пользовательскими.** Ошибка типа `E9xxx` означает баг в компиляторе.

## Что не является диагностикой

- **Отсутствие `default` в `switch`.** Не ошибка, не предупреждение. `switch` без `default` просто ничего не делает, если ни один `case` не совпал.
- **Неиспользуемая переменная.** Пока не диагностируется. В v1 не проверяется.
- **Недостижимый код после `return`.** Пока не диагностируется.
- **`try` без `throws`.** Не диагностируется.
- **Отсутствие `return` в функции с ненулевым возвратом.** Пока не диагностируется.
- **Неинициализированное `let`.** Генерируется `undefined`, ошибки нет.

## Планируемый формат CLI

```
<path>:<line>:<col>: <severity>[<code>]: <message>
   |
<line> | <source line>
   | <пробелы>^ <подсказка>
   |
   = help: <как исправить>
```

Пример:

```
src/main.sws:12:5: error[E0004]: expected `{`, got `foo`
   |
12 | func greet(name: String) -> String
   |                                   ^ expected `{` here
   |
   = help: функция должна иметь тело в фигурных скобках
```

Цвета:

| Элемент | Цвет |
|---------|------|
| `error` | красный |
| `warning` | жёлтый |
| `help` | голубой |
| `^` | красный или жёлтый по уровню |
| Строка исходника | обычный |

Отключение цвета: `--color=never`. Флаг `--color=auto` (по умолчанию) отключает цвет, если stderr не TTY.

## Открытые вопросы

❓ **Коды ошибок.** Сейчас кодов нет, только текст. Введение кодов улучшит поиск по документации и автоматическую обработку, но потребует пересмотра всех сообщений. Стоит ли вводить коды сейчас, или после type checker'а?

❓ **Приоритеты ошибок.** Компилятор сообщает только первую ошибку. Это упрощает реализацию, но замедляет отладку. Когда переходить к выводу всех ошибок?

❓ **Позиции в кодогенераторе.** Без позиций в AST ошибки кодогенератора не могут указать место. Стоит ли добавить позиции в AST, чтобы даже внутренние ошибки были полезны?

❓ **Позиция для `if let` и `guard let`.** Если checker найдёт ошибку в развёртке опционала, где указывать позицию — в `let` или в `if`/`guard`? Это нужно решить до реализации checker'а.

❓ **Локализация.** Сейчас сообщения на русском. Если язык будет использоваться кем-то ещё, понадобится английский. Стоит ли сразу писать сообщения на английском, или оставить русский для v1?

❓ **Предупреждения об именах.** Имена `_self`, `_sw<N>`, `_s<N>`, `_0`, `_force`, `_range` конфликтуют с внутренними. Стоит ли ввести предупреждение при их использовании?

❓ **Сообщения об ошибках в `switch`.** «В switch ожидался case или default» — не говорит, какой именно токен ожидался вместо чего. Стоит ли различать «ожидался `case`» и «ожидался `default`»?
