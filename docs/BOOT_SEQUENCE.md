# BOOT_SEQUENCE.md

Спецификация стадий компиляции SwiftScript. Документ описывает, что происходит между вызовом `swsc` и записью `.js`. Если код и документ расходятся — это баг.

## Обзор

Компиляция — линейный конвейер из стадий. Каждая стадия потребляет выход предыдущей и производит свой. Промежуточные данные не сохраняются между запусками.

**Принцип:** одна стадия — одна ответственность. Стадия либо завершается успешно, либо бросает ошибку. Частичный результат не передаётся дальше.

## Стадии

```
[1] Read     →  source text
[2] Lex      →  tokens
[3] Parse    →  AST
[4] Check    →  typed AST (планируется)
[5] Emit     →  JS string
[6] Wrap     →  final JS (runtime + user code)
[7] Write    →  file on disk
```

В v1 стадии 4 нет. Она появится после реализации checker'а.

## Стадия 1: Read

**Вход:** путь к `.sws`-файлу.
**Выход:** строка с содержимым файла.

**Что делает:**

1. Открывает файл на чтение.
2. Читает всё содержимое в память.
3. Возвращает строку.

**Ошибки:**

| Условие | Код | Поведение |
|---------|-----|-----------|
| Файл не существует | ENOENT | `swsc: cannot read <path>: ENOENT`. Exit 2 |
| Нет прав на чтение | EACCES | `swsc: cannot read <path>: EACCES`. Exit 2 |
| Файл не UTF-8 | — | В v1 — не проверяется |

> ℹ️ **Примечание:** файл читается целиком. Для больших файлов (десятки МБ) это может быть проблемой. В v1 — не оптимизируется.

**Побочные эффекты:** нет. Read не модифицирует входной файл.

## Стадия 2: Lex

**Вход:** строка исходника.
**Выход:** массив токенов, последний — `eof`.

**Что делает:**

1. Проходит по строке слева направо.
2. Пропускает пробелы и комментарии.
3. Распознаёт токены по правилам из [LEXER_SPEC.md](LEXER_SPEC.md).
4. Присваивает каждому токену позицию `(line, col)`.
5. Добавляет `eof` в конец.

**Ошибки:**

| Условие | Сообщение |
|---------|-----------|
| Незакрытая строка | `Незакрытая строка` |
| Неизвестный символ | `Неизвестный символ '<c>'` |

Позиция ошибки — токен, на котором лексер споткнулся.

**Гарантии:**

- Число токенов конечно.
- Позиции монотонно неубывают.
- `eof` всегда последний.

**Побочные эффекты:** нет.

## Стадия 3: Parse

**Вход:** массив токенов.
**Выход:** узел `Program` с полным AST.

**Что делает:**

1. Устанавливает позицию в начало массива.
2. Рекурсивно разбирает statements по правилам из [GRAMMAR.md](GRAMMAR.md).
3. Строит AST по схеме из [AST_SCHEMA.md](AST_SCHEMA.md).

**Ошибки:**

| Условие | Сообщение |
|---------|-----------|
| Неожиданный токен | `Неожиданный токен '<v>'` |
| Ожидался один токен, получен другой | `Ожидалось <kind>, получено '<got>'` |
| Незакрытый блок | `Незакрытая функция` / `Незакрытый блок` / ... |
| Интерполяция не выражение | `Интерполяция должна быть выражением` |
| `async` не перед лямбдой | `async должен стоять перед лямбдой` |

**Гарантии:**

- AST не содержит `null` в обязательных полях.
- AST не содержит ссылок на токены.
- AST не содержит циклов.

**Побочные эффекты:** нет. Парсер не пишет файлы, не обращается к сети.

**Остановка при ошибке.** Парсер не восстанавливается. Первая ошибка — последняя.

## Стадия 4: Check

**Статус:** планируется.

**Вход:** AST.
**Выход:** AST с прикреплённой информацией о типах.

**Что будет делать:**

1. Строит таблицу символов.
2. Проходит по AST, выводя типы.
3. Проверяет совместимость по правилам из [TYPE_SYSTEM.md](TYPE_SYSTEM.md).
4. Собирает ошибки типов.

**Ошибки:** коды `E1xxx`, `E2xxx` из [DIAGNOSTICS.md](DIAGNOSTICS.md).

**Поведение при ошибке:** компиляция останавливается. Emit не выполняется. JS не генерируется.

> ℹ️ **Примечание:** check — единственная стадия, которая может вернуть **несколько** ошибок за один проход. Все остальные возвращают первую.

**Когда появится:** после того, как базовый язык стабилизируется. До этого `swsc build` работает без проверки типов.

## Стадия 5: Emit

**Вход:** AST (в будущем — типизированный).
**Выход:** строка с пользовательским JavaScript.

**Что делает:**

1. Обходит AST.
2. Для каждого узла вызывает `genStmt` или `genExpr`.
3. Собирает выход в одну строку.

**Ошибки:**

| Условие | Сообщение |
|---------|-----------|
| Неизвестный узел AST | `Кодоген: неизвестное выражение <k>` |
| Неизвестный паттерн | `Кодоген: неизвестный паттерн <k>` |
| Структура с безымянным аргументом | `Структура <name>: аргументы должны быть именованными` |

> ⚠️ **Внимание:** все ошибки кодогенератора — это **баги компилятора**. Пользователь не должен их видеть. Если видит — это значит, что парсер произвёл невалидный AST или checker пропустил невалидную программу.

**Гарантии:**

- Выход — валидный JavaScript в смысле синтаксиса.
- Все идентификаторы из исходника сохранены (кроме `_self`-префиксации).
- Все типы стёрты.

**Побочные эффекты:** нет. Emit не пишет файлы.

## Стадия 6: Wrap

**Вход:** строка с пользовательским JS.
**Выход:** строка с полным JS (runtime + пользовательский код, опционально в IIFE).

**Что делает:**

1. Проверяет, есть ли в пользовательском коде `import` или `export` через регулярное выражение `^\s*(import|export)\b/m`.
2. Если есть — конкатенирует `RUNTIME + "\n" + userJs`.
3. Если нет — оборачивает в IIFE: `RUNTIME + "\n(() => {\n" + userJs + "\n})();"`.

**Ошибки:** нет. Wrap не может провалиться.

**Гарантии:**

- Runtime всегда в начале файла.
- IIFE добавляется только для не-модульных программ.

> ⚠️ **Внимание:** проверка на `import`/`export` — регулярное выражение, не разбор AST. Строка `"export"` внутри строкового литерала может быть ошибочно распознана как модульный код.

**Побочные эффекты:** нет.

## Стадия 7: Write

**Вход:** строка с полным JS и путь для записи.
**Выход:** файл на диске.

**Что делает:**

1. Проверяет, существует ли директория для записи.
2. Если нет — создаёт рекурсивно.
3. Открывает файл на запись.
4. Пишет содержимое.
5. Закрывает.

**Ошибки:**

| Условие | Код | Поведение |
|---------|-----|-----------|
| Нет прав на запись | EACCES | `swsc: cannot write <path>: EACCES`. Exit 2 |
| Диск переполнен | ENOSPC | `swsc: cannot write <path>: ENOSPC`. Exit 2 |
| Директория недоступна | ENOENT | `swsc: cannot write <path>: ENOENT`. Exit 2 |

**Поведение при перезаписи:** существующий файл заменяется без предупреждения.

> ⚠️ **Внимание:** запись не атомарна. Если процесс прервётся между открытием и закрытием файла, файл может быть повреждён. Для атомарности писать во временный и переименовывать.

**Побочные эффекты:** файл на диске.

## Общий конвейер

```js
function compile(src) {
    // Стадии 2, 3, 4, 5
    const tokens = tokenize(src);          // [2] Lex
    const ast = parse(tokens);             // [3] Parse
    // check(ast);                         // [4] Check (планируется)
    const userJs = genProgram(ast);        // [5] Emit
    
    // Стадия 6
    const hasModuleSyntax = /^\s*(import|export)\b/m.test(userJs);
    const js = hasModuleSyntax
        ? `${RUNTIME}\n${userJs}`
        : `${RUNTIME}\n(() => {\n${userJs}\n})();`;
    
    return { js, userJs, diagnostics: [] };
}
```

Стадии 1 и 7 — вне `compile()`. Они выполняются вызывающим кодом (`app.js` в браузере, `swsc` в CLI).

## Обработка ошибок

При ошибке любой стадии:

1. Стадия бросает `SSError` с позицией.
2. `compile()` перехватывает, превращает в диагностику, возвращает пустой `js`.
3. `swsc` печатает диагностику в stderr, возвращает exit code.

**Порядок вывода:** диагностики выводятся в порядке появления. Если ошибка в лексере — парсер и emit не выполняются.

> ℹ️ **Примечание:** в v1 компилятор останавливается на первой ошибке. Check (стадия 4) будет исключением — он может собрать несколько ошибок за один проход.

## Детерминизм

Для одного и того же входа `.sws` и одной и той же версии `swsc` выход **детерминирован**.

**Исключение:** счётчик `_swCounter` в codegen глобальный. При повторной компиляции в одном процессе метки `_swN` будут другими. Это влияет на **текст** выхода, но не на **семантику**.

Для byte-identical выхода между запусками нужно сбрасывать `_swCounter` в начале каждого `compile()`. В v1 — не делается.

## Производительность

Порядок величин для файла 1000 строк:

| Стадия | Время |
|--------|-------|
| Read | < 1 ms |
| Lex | ~ 1 ms |
| Parse | ~ 3 ms |
| Emit | ~ 2 ms |
| Wrap | < 1 ms |
| Write | < 1 ms |
| **Итого** | **~ 8 ms** |

Для проекта из 100 файлов — около секунды.

> ℹ️ **Примечание:** цифры ориентировочные. Зависят от размера файлов, скорости диска и загрузки CPU.

## Что происходит в watch-режиме

1. Выполняется полная компиляция один раз.
2. Устанавливается watcher на директорию.
3. При изменении `.sws`:
   - Определяется затронутый файл.
   - Запускается полный конвейер для этого файла.
   - Остальные файлы не трогаются.
4. При появлении нового `.sws` — компилируется.
5. При удалении `.sws` — соответствующий `.js` **не** удаляется.

> ⚠️ **Внимание:** в watch-режиме `_swCounter` продолжает расти. Файлы, скомпилированные после первого, будут иметь метки `_swN` с большими N.

## Открытые вопросы

❓ **Стадия 4 (Check).** Когда появится. Что будет проверяться в первой версии. Как будет взаимодействовать с парсером — отдельный проход или встроено.

❓ **Диагностики на всех стадиях.** Сейчас каждая стадия бросает `SSError`. Check будет собирать массив. Стоит ли унифицировать интерфейс всех стадий — возвращать массив диагностик, а не бросать.

❓ **Отслеживание зависимостей.** В watch-режиме изменение одного файла не пересобирает зависимые. Стоит ли это делать.

❓ **Byte-identical выход.** Счётчик `_swCounter` глобальный. Стоит ли сбрасывать его в начале каждого `compile()`, чтобы выход был детерминирован между запусками.

❓ **Атомарная запись.** Сейчас файл пишется напрямую. Стоит ли писать во временный и переименовывать.

❓ **Check на top-level.** Если появится checker, должен ли он проверять top-level имена. Например, `let x = 5` без использования — предупреждение W0001.

❓ **Прогресс для больших проектов.** При сборке сотни файлов вывод «тихо». Стоит ли добавить прогресс-бар.
