# PROJECT_LAYOUT.md

Спецификация организации проектов на SwiftScript. Документ описывает, как структурировать код, как работают модули и как компилятор обходит файлы. Если код и документ расходятся — это баг.

## Обзор

Проект на SwiftScript — это директория с файлами `.sws` и опциональным `swsc.config.json`. Никакой обязательной структуры нет. Компилятор обходит файлы рекурсивно и превращает каждый `.sws` в `.js` с сохранением относительных путей.

**Обязательного манифеста нет.** Аналога `package.json` или `Cargo.toml` в v1 не существует. Конфиг опционален.

## Минимальный проект

```
hello/
├── hello.sws
└── hello.js          — генерируется
```

```swift
// hello.sws
print("Hello, World!")
```

```bash
swsc build hello.sws
node hello.js
```

Никаких других файлов не требуется.

## Типичный проект

```
myproject/
├── swsc.config.json      — опциональная конфигурация
├── src/
│   ├── main.sws
│   ├── lib/
│   │   ├── utils.sws
│   │   └── io.sws
│   └── models/
│       ├── user.sws
│       └── post.sws
└── build/                — генерируется
    ├── main.js
    ├── lib/
    │   ├── utils.js
    │   └── io.js
    └── models/
        ├── user.js
        └── post.js
```

Структура `src/` повторяется в `build/` без изменений. Имена файлов сохраняются, расширение меняется с `.sws` на `.js`.

## Конфигурация

`swsc.config.json` в корне проекта:

```json
{
    "src": "src",
    "out": "build",
    "strict": false,
    "target": "es2022",
    "runtime": true
}
```

| Поле | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `src` | `string` | `"src"` | Директория с исходниками |
| `out` | `string` | `"build"` | Выходная директория |
| `strict` | `boolean` | `false` | Предупреждения становятся ошибками |
| `target` | `string` | `"es2022"` | Целевая версия JS |
| `runtime` | `boolean` | `true` | Встраивать runtime в каждый файл |

Конфиг **опционален**. Без него `swsc build src/ -o build/` работает так же.

> ❓ **Требуется уточнение:** где искать `swsc.config.json`. В `cwd`, в родительских директориях, в директории `package.json`. См. открытые вопросы.

## Модули

Модуль — это файл `.sws`. Два модуля связаны через `import`/`export`.

### Экспорт

```swift
// lib/utils.sws

export let version = "1.0"

export func greet(name: String) -> String {
    return "Hello, \(name)!"
}

export func add(a: Int, b: Int) -> Int {
    return a + b
}

let internalHelper = "not exported"

func helper() -> String {
    return internalHelper
}
```

`export` перед объявлением делает имя доступным для импорта. Без `export` имя доступно только внутри модуля.

### Импорт с именами

```swift
// main.sws

import { greet, add } from "./lib/utils.sws"

print(greet("World"))
print(add(2, 3))
```

Импортированные имена вводятся в область видимости файла.

### Импорт с переименованием

```swift
import { greet as hello, add as sum } from "./lib/utils.sws"

print(hello("World"))
print(sum(2, 3))
```

### Импорт всего

```swift
import * as utils from "./lib/utils.sws"

print(utils.greet("World"))
print(utils.add(2, 3))
```

Импортируется объект со всеми экспортированными именами.

### Импорт по умолчанию

```swift
import defaultExport from "./module.sws"
```

Если модуль имеет экспорт по умолчанию. В SwiftScript нет синтаксиса для default export. `import X from "..."` эквивалентен `import * as X from "..."`.

> ❓ **Требуется уточнение:** нужен ли `export default`. В Swift его нет. В JS — есть.

### Правила импорта

1. **Путь — строка.** Относительный (`./`, `../`) или абсолютный.
2. **Расширение указывается.** `"./utils.sws"`, не `"./utils"`.
3. **Циклы запрещены.** `a.sws` → `b.sws` → `a.sws` — ошибка.
4. **Повторный импорт — идемпотентен.** `import { x } from "./a.sws"` дважды в одном файле — ошибка E2001.
5. **Модуль компилируется один раз**, независимо от числа импортов.

> ⚠️ **Внимание:** в сгенерированном JS импорты остаются как `import`. Резолвинг — работа среды выполнения (Node.js, bundler). `swsc` не собирает модули в один файл.

## Соглашения

Никаких **обязательных** соглашений нет. Компилятор не требует конкретных имён файлов, конкретной структуры директорий или конкретного стиля кода.

**Рекомендуемые** соглашения (из практики):

| Что | Как |
|-----|-----|
| Точка входа | `main.sws` |
| Библиотеки | `lib/` |
| Модели | `models/` или рядом с использованием |
| Тесты | `tests/` или `*.test.sws` |
| Имя файла | `snake_case.sws` или `kebab-case.sws` |
| Имя функции | `camelCase` |
| Имя типа | `PascalCase` |
| Имя константы | `SCREAMING_SNAKE` или `camelCase` |

Это **соглашения, не правила**. Компилятор их не проверяет.

## Обход файлов

При передаче директории `swsc` обходит её рекурсивно:

1. **Включаются** файлы с расширением `.sws`.
2. **Пропускаются** директории: `node_modules`, `.git`, `.svn`, `.hg`, `build`, `dist`, `out`.
3. **Пропускаются** файлы, начинающиеся с `.` (`.DS_Store`, `.gitignore`).
4. **Порядок обхода:** алфавитный по возрастанию, сначала файлы, потом поддиректории.

> ⚠️ **Внимание:** если `out` внутри `src`, компилятор исключает его из обхода. Это позволяет использовать `swsc build src/ -o src/build/`, но не рекомендуется.

## Связь между файлами

`swsc` **не отслеживает зависимости**. Каждый файл компилируется независимо. Импорты разрешаются **в среде выполнения**, не компилятором.

Это значит:

- Изменение `utils.sws` **не** вызывает перекомпиляцию `main.sws` в режиме `build`.
- В режиме `watch` изменение `utils.sws` пересобирает **только** `utils.js`.
- Импорты резолвятся Node.js при запуске.

> ⚠️ **Внимание:** если `utils.sws` экспортировал `greet`, а после изменения — `hello`, `main.js` не перекомпилируется, и при запуске будет ошибка импорта. Для полной пересборки запустите `swsc build` заново.

> ❓ **Требуется уточнение:** нужна ли инкрементальная сборка с отслеживанием зависимостей. В v1 — нет.

## Runtime

Runtime встраивается в **каждый** скомпилированный файл. Для проекта из 10 файлов runtime появится 10 раз.

**Решения:**

| Подход | Как |
|--------|-----|
| Встроить везде | По умолчанию. Работает, но дублирует код |
| Встроить один раз | Собрать с `--no-runtime` и подключить вручную |
| Отдельный модуль | `import { print } from "./runtime.sws"` — **не поддерживается** в v1 |

> ℹ️ **Примечание:** в v1 рекомендуется встраивать runtime везде. Размер — 1.5 КБ на файл. Для проекта из 10 файлов — 15 КБ. Для продакшена — использовать bundler (rollup, esbuild), который дедуплицирует.

## Работа с build

`swsc build src/ -o build/` создаёт зеркальную структуру:

```
src/a/b/c.sws   →   build/a/b/c.js
```

Файлы в `build/` **не удаляются**, если соответствующий `.sws` удалён. Для очистки — удалить `build/` вручную.

> ❓ **Требуется уточнение:** флаг `--clean` для очистки `out` перед сборкой. В v1 — не поддерживается.

## Открытые вопросы

❓ **Поиск конфига.** Где искать `swsc.config.json`. В `cwd`, в родительских директориях, в директории с `package.json`?

❓ **Реэкспорт.** `export { X } from "./a.sws"` — нужен ли. В Swift такого нет, но в крупных проектах удобен.

❓ **`export default`.** В Swift нет. В JS есть. Нужен ли в SwiftScript.

❓ **Отслеживание зависимостей.** Инкрементальная сборка с учётом импортов. Стоит ли делать в v1.

❓ **Пакеты.** Будет ли когда-нибудь реестр модулей и `swsc install`. В v1 — нет, и не планируется.

❓ **Директория `tests/`.** Как запускать тесты. Отдельная команда `swsc test` или через внешний test runner.

❓ **`node_modules`.** Если пользователь хочет использовать npm-пакет, как это делается. Через `import x from "package"` или через `import x from "./node_modules/package/index.js"`.

❓ **Абсолютные пути.** `import { x } from "/home/user/project/lib.sws"` — разрешено. Или только относительные.

❓ **Симлинки.** Если `src/lib` — симлинк на другую директорию, обходить ли её. По умолчанию — да.

❓ **`swsc build` без `src/`.** Если в директории нет поддиректории `src/`, но есть `.sws` в корне — компилировать? Текущее поведение — компилировать всё, что найдено в `<path>`.
